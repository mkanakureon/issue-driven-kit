# 設計・実装・テストの回し方（ゴール → 合格の条件 → 設計 → 実装 → テスト → NG の振り分け → 判定）

Issue 駆動キットの元のリポジトリ（kaedevn・KaedeScapeBuii）で、ユーザーの指示のもと形にした回し方。
ユーザーの言葉: 「設計、実装、テストのループを徹底して」「設計がただしければ、テストが少なくて済むしNGもでない、設計書を詳細にして」「テストNGは設計書を確認して設計がだめなのか？実装がまちがったのかを明確にして改善サイクルを回して」「合格判定した？」。

## 0. やってはいけないこと（この回し方を作ったときに実際にした失敗）

- 設計を書かずに、思いついた順に作る（あとで設計に合わせて作り直すことになった）。
- 機械の確かめ（テストが通った）だけで「できた」と報告し、**ゴールの合格判定をしない／人に回す**。
- ユーザーの指示を都合よく読み替える（「プレイ画面にないものはいみがない」を「撮らない」と読んだ。正しくは「プレイ画面に出る形にする」）。
- 確かめずに「合格」と書く（入力を間違った引数で渡し、何もしないまま「合格」と出ていた）。vitest では、`-t` の名前の書き間違いで 0 件のまま終わるのが同じ形（`scripts/test.mjs` は 0 件を FAIL にする）。
- 設計で決めていない固定値をテストの合格条件にする（所持金 137 は道が変わると変わる）。
- **違うものどうしを比べて判定する**（比べる相手に何が入っているかを見ずに選んでいた）。
- **作った本人が判定する**（直した所ばかり見て「以上」を付けた。ユーザー: 「これが繰り返されると困る、単に間違ってましたでは」）。

## 1. ゴールと合格の条件を先に決める（設計書の §0）

1. **ゴール**をユーザーの言葉で 1 文に書く。「誰が・何を見て・どう判断するか」まで（例: 利用者がマイナスのスコアを送ると、400 と理由が返り、ランキングに載らないのを見て、不正が弾かれたと分かる）。
2. ゴールを測れる**合格の条件**の表にする。条件ごとに「誰が・どう確かめるか」を書く。
   - 機械（毎回・テストの合否）: vitest のテスト・型の確かめ・出力のファイル・HTTP の応答。
   - AI の判定（報告の前に必ずする）: 比べる相手（仕様・手本）と並べ、決めた確かめの表（見る所）と判定の決め方で判定し、記録する。
   - ユーザーの最終判定: 機械で測れない実感（使い心地・見た目）。AI の判定は観測の記録で、ユーザーが決める（CLAUDE.md 原則 4）。
3. ゴールに届かない条件が 1 つでもあれば、**「できた」と報告しない**。途中で報告するときは「合格していない・どれが届いていないか」を書く。

## 2. 設計書を詳しく書く（常設の文書）

- 置き場は `docs/guides/working/<機能>-design.md`（CLAUDE.md の「置き場」）。書き方は `document-authoring` スキル。
- **事実を先に確かめてから書く**（ソース・実行結果・API の応答・DB の定義）。推測で決めない。
- 実装とテストがそのまま書けるところまで決める: 何を作るか（表）・作る順・データの形（型・JSON・テーブル）・モジュールの分け方・確かめ（どれが落ちたら失敗か）・テストの名前・NG のときの扱い。
- 番号・一覧・調整値は**データ 1 か所**（定数のモジュールか設定のファイル）に置き、コードのあちこちに直に書かない。
- **ロジックは入出力（HTTP・DB）から外へ出す**（ふつうの関数）。速い単体の試験で確かめられる範囲を広げるため。Worker と DB を通す試験は、それが要るものだけ。
- 指示の表を付ける（指示をそのまま引き、設計のどこで答えるか）。指示を読み替えていないかをここで確かめる。

## 3. 実装は設計どおり

- 設計と違うことをしたくなったら、**先に設計書を直してから**実装する。
- 実装の途中で設計の穴に気づいたら、その場で設計書に書き足す（「設計の抜け」として記録）。

## 4. テスト

1. 機械の確かめ: `node scripts/test.mjs`（手順は `docs/guides/procedures/node-test-procedure.md`）。合否は `Result:` 行で読む。
2. 実物を見る（応答・出力・画面）。「見ていない」ものを「確かめた」と書かない。
3. **合格判定（§1 の AI の判定）を報告の前にする**。比べる相手が無ければ、まず用意する。用意できないものは「未判定」と書き、合格にしない。
4. **比べられるかを先に決める**: 比べる 2 つに入っているものをデータに 1 行ずつ書き、同じでなければ「比べられない」として判定しない。設計を直す。
5. **判定は作った本人がしない**: その回の実装をしていない判定役（新しいエージェント。何を直したかは渡さない。ゴール・実行結果の場所・手順だけ渡す）に判定させる。迷ったら低い方。実装した側は判定役の結果を写すだけで、判定を上げない。

## 5. NG の振り分け（テストの失敗・判定の「劣る」）

1. 設計書のどこに当たるかを見る。
2. 設計どおりに作っていて結果が悪い → **設計がだめ（抜け・誤り）**。先に設計書を直してから実装を直す。
3. 設計と実装が違う → **実装の誤り**。実装を直す。
4. 判定で「劣る」が付いたら、設計書に直し方の表（場面・何が劣るか・直し方・直す所）を足してから実装する。
5. その日の `docs/reports/YYYY/MM/DD/` に「現象・設計の該当・判定（設計／実装）・直したこと・確かめ」を 1 行ずつ残す。

## 6. 回す

テスト → 振り分け → 設計（必要なら）→ 実装 → テスト → 判定、を合格の条件が全部満たされるまで回す。
報告には: ゴール・合格の条件ごとの結果（満たした／満たさない／未判定）・この回で直した NG（設計か実装か）・残り。

大きいものを無人で回すなら、設計書を書く Issue と実装する Issue に分ける（`github-issue` スキル・`docs/guides/procedures/issue-goal-setting.md`）。
