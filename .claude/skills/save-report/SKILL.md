# レポート保存 Skill（Node.js＋TypeScript 用）

作業の振り返り・設計文書・調査結果・API の確かめの記録などを `docs/reports/` に保存する。

## 保存先ルール

```
docs/reports/{年}/{月}/{日}/{連番}-{タイトル}.md
```

例: `docs/reports/2026/10/23/01-api-contract-check-report.md`

- **年月日**: 今日の日付を使う（`YYYY/MM/DD`、ゼロ埋め）
- **連番**: その日のフォルダ内の**最大の番号 + 1**（ゼロ埋め2桁）。
  **ファイル数ではなく最大値で決める**——欠番があると数え方では衝突する。
  **書く直前に `ls` する。** 元のリポジトリで、別セッションと同じ日に書いて 3 回ぶつかった。
  番号は早い者勝ちに見えて、**連番でひとつの話になっている側を崩さない**のが優先。
  ぶつかったら、単独の文書のほうを空き番号へ動かす（`git mv` で履歴を繋ぐ）。
  無人の回のまとめ（`NN-issue-run.md`）も同じフォルダーに同じ数え方で入る。
- **タイトル**: 英語ケバブケース、内容を簡潔に表す
- パスは**いまの worktree のルート**基準（別 worktree へ保存しない）

### 種別サフィックス

タイトルの末尾に種別を付けて区別する（サブフォルダーは作らない）。

| 種別 | サフィックス | 例 |
|---|---|---|
| 計画書 | `-plan` | `03-phase1-plan.md` |
| 設計書・仕様書 | `-spec` / `-design` | `01-ranking-spec.md` |
| 実装・作業レポート | `-report` | `06-auth-report.md` |
| リファレンス（一覧・コマンド集） | `-reference` | `01-wrangler-command-reference.md` |
| 手順書 | `-guide` / `-procedure` | `04-local-d1-guide.md` |
| ステータス報告 | `-status` | `08-phase1-status.md` |
| 調査の記録 | `-investigation` | `02-d1-limits-investigation.md` |

## 手順

1. 今日のフォルダを確認: `ls docs/reports/YYYY/MM/DD/`
2. 既存ファイルの**最大番号 + 1** を連番にする（`ls` して確認。ファイル数で決めない）
3. フォルダがなければ作成: `mkdir -p docs/reports/YYYY/MM/DD`
4. ファイルを作成

## デフォルト保存先のルール

**保存先が明示されていない場合、常に `docs/reports/` を使う。**

- 「ここに保存して」→ `docs/reports/` に保存
- 「文書を作って」「表を作って」「まとめて」など、保存先の言及がない場合も `docs/reports/` に保存
- 別の場所への保存は、ユーザーが明示的にパスを指定した場合のみ

## 書き込み禁止ディレクトリ

**以下のディレクトリには文書を書き込まない。**

| ディレクトリ | 理由 |
|---|---|
| `src/` | コードの置き場。文書を混ぜない |
| `node_modules/` `dist/` `coverage/` `.wrangler/` | 生成物。作り直すと消える |
| `.issue-run/` | 無人の回のログ（追跡しない）。スクリプトの出力の置き場 |
| `docs/inspecs/` | **人が書く入力の文書の置き場**。Claude は読むだけで、書き換えない・作らない（入力から作った文書は `docs/reports/` へ） |

- 種別（仕様/設計/レポート/調査）に関わらず、Claude が作成する文書はすべて `docs/reports/` に保存する（更新し続ける設計書は `docs/guides/working/`）
- ログの実体（`.issue-run/logs/...` など）を文書から参照するのは可。文書本体は `docs/reports/` に置く

## 既存ファイルの扱い

会話中にすでにプロジェクト直下などへ作成されてしまった `.md` がある場合：

- 移動はしない（既存ファイルはそのままにする）
- 代わりに `docs/reports/` へ内容をまとめたレポートを作成する

### 重要: 暗黙のトリガー

ユーザーが「保存」「文書」「ドキュメント」「md」「まとめ」などのキーワードを含む指示をした場合、
保存先が明示されていなくても `docs/reports/` を保存先とみなして発動する。

## レポートのフォーマット

```markdown
---
generated_by: Claude {現在のモデル名}
date: {YYYY-MM-DD}
type: {report | spec | plan | guide | status | reference | investigation}
project: {リポジトリの名前}
---

# タイトル

> Generated by Claude {現在のモデル名} — {YYYY}年{M}月{D}日

## 背景
（なぜこの作業が必要だったか）

## 方針 / 設定
（アプローチ。API なら要求と応答・設定の値）

## 手順
（再現できるステップ。コマンドを具体的に）

## 成果物 / 出力先
| # | ファイル | 内容 |
|---|---------|------|
| 1 | `src/rankings.ts` | 検証の関数 |

## 教訓 / 次回への申し送り
（今後に活かせるポイント）

---

> この文書は Claude {現在のモデル名} が生成しました。内容の正確性は人間のレビューを経て確認してください。
>
> Claude {現在のモデル名} — Anthropic
```

### ヘッダー（YAML frontmatter）— 必須

| フィールド | 値 | 説明 |
|-----------|-----|------|
| `generated_by` | `Claude {現在のモデル名}` | 生成したモデル名（例: `Claude Opus 5.5`） |
| `date` | `YYYY-MM-DD` | 生成日 |
| `type` | サフィックスに対応する種別 | `report`, `spec`, `plan`, `guide`, `status`, `reference`, `investigation` のいずれか |
| `project` | リポジトリの名前 | `package.json` の `name` |

### フッター（署名ブロック）— 必須

- `---` で本文と区切る
- 1行目: 免責（「人間のレビューを経て確認してください」）
- 2行目: 空の引用行（`>`）
- 3行目: モデル署名 `Claude {現在のモデル名} — Anthropic`
- `{現在のモデル名}` にはセッション実行時の実際のモデル名を記入する（例: `Opus 5.5`、`Sonnet 5.5`）

### その他のルール

- セクションは内容に応じて取捨選択する（全部必須ではない）
- API や DB の確かめの文書では、要求・応答・状態コード・使ったコマンドを必ずそのまま残す（後で同じ確かめを再現するため）
- 本文は日本語、コード・識別子・パスは英語
