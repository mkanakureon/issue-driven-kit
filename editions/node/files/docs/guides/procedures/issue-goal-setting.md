# ゴールを決めて Issue に書く手順（無人の Claude に渡す前に）

ユーザーが書くもの・書き方・Issue への載せ方の正。無人で回す仕組みは `docs/guides/working/issue-run.md`、回し方の中身（ゴール → 合格の条件 → 設計 → 実装 → テスト → 振り分け → 判定）は `.claude/skills/design-cycle/SKILL.md`。会話の中で Claude に作らせるなら `github-issue` スキル。

Issue 駆動キットの元のリポジトリ（kaedevn・KaedeScapeBuii）の同じ文書を、Node.js＋TypeScript（vitest）向けに書き直した。確認コマンドは ```` ```js ```` の塊（ES モジュール）で書く。

## 0. 流れ

```
① 決める（ユーザー）
   ↓
② 文書を書く … 大きいものは設計書。小さいものは要らない
   ↓
③ Issue を書く … 札（元の文書・合格の条件・確認コマンド）
   ↓
④ 試す … node scripts/issue-run/issue-run.mjs --dry-run
   ↓
⑤ 起動 … node scripts/issue-run/issue-run.mjs。人が作業していない worktree を選ぶ
   ↓
⑥ 確認（終わった後） … まとめ → Issue のコメント → 閉じる／直して出し直す
```

**一番大事なのは③の「確認コマンド」。** 無人の Claude は、確認コマンドが exit 0 になるまで終われない。逆に言えば、確認コマンドが通れば終わる。確認コマンドがゴールそのものになる、と思って書く。

## 1. どの文書を書くか

| やりたいことの大きさ | ユーザーが書くもの | Claude に任せられるもの |
|---|---|---|
| **小さい**（バグを1つ直す・値を数件足す・文言を直す） | Issue だけ。「元の文書」には今ある文書の該当の節を書く | 実装・テスト |
| **中くらい**（既存の設計書の1節を実装する） | Issue だけ。設計書のその節に合格の条件が書いてあれば、Issue はそれを指す | 実装・テスト |
| **大きい**（新しい機能・新しい API・仕組みの変更） | **2回に分ける。** 1回目は「設計書を書く」Issue、終わったら設計書を読んで直す、2回目に「実装する」Issue | 1回目: 設計書の下書き／2回目: 実装・テスト |
| **方針が決まっていない**（やるかどうか・どちらの方式か） | Issue にしない。先に決める（決めたら `docs/guides/decisions/` に書く） | — |

設計が正しければ、実装のやり直しが減る（design-cycle）。設計の良し悪しはユーザーが読まないと決まらないので、大きいものは無人の回の間にユーザーの確認を1回はさむ。

## 2. ゴールを1文で書く

「誰が・何を見て・どう判断するか」まで書く（design-cycle §1）。

| 悪い | 良い |
|---|---|
| スコアの検証を作る | マイナスのスコアを送ると 400 と理由が返り、ランキングに載らない |
| テストを強くする | `スコアの投稿` の試験が、整数でないスコアも 400 になることを確かめる |
| 使いやすくする | （無人には向かない。ユーザーが触って決める。→ 3.2） |

## 3. 合格の条件を書く

### 3.1 公式の3要素

1. **測れる終わりの状態が1つ** — テストの結果・終了コード・件数・ファイルがあるか
2. **確かめ方** — どのコマンドで、何が出たら合格か
3. **途中で変えてはいけないもの** — テスト・既存のデータ・ほかの機能

### 3.2 Issue に入れてよい条件・入れない条件

| 種類 | 例 | 無人の Issue では |
|---|---|---|
| 機械（コマンドで合否が出る） | テストが通る・型の確かめが通る・ファイルに節がそろっている | **合格の条件に入れ、確認コマンドで全部確かめる** |
| AI の判定（比べる相手と並べて判定） | 仕様の文と並べて、応答の書き方が以上か | 合格の条件に入れない。「やらないこと」に「判定はしない。記録まで」と書く |
| ユーザーの判定（実感） | 使って気持ちいいか・読みやすいか | 合格の条件に入れない。終わった後にユーザーがやる |

機械で測れない条件を入れると、Claude は自分で「合格」と書くしかなくなる。それが公式の言う一番の失敗（早すぎる勝利宣言）。

AI の判定をさせたいときは、合否の外に置いて書く: 「AI の判定が要る条件（設計書 §0.2 の F2）は、報告の前に判定役（作った本人でない別のエージェント）にさせて、結果を報告に書く（合否には入れない）」。

### 3.3 箇条書きと確認コマンドを対応させる

箇条書きの1行ずつが、確認コマンドのどこかで確かめられるようにする。確かめられない行は書かない（書くなら「やらないこと」へ）。

## 4. 確認コマンドを書く

Issue の「## 合格の条件」の中に ```` ```js ```` で書く。**リポジトリの直下で、`node` に ES モジュールとして渡されて実行され、exit 0 なら合格。** `import` の相対パスはリポジトリの直下から解決される。

### 4.1 既存の入口と手伝い

`scripts/issue-run/check-lib.mjs` の手伝いを読み込んで使う。

| 手伝い | 何をする | 落ちたとき |
|---|---|---|
| `runTests({ filter, file })` | テストの入口（`scripts/test.mjs`）を回し、最後の行が `Result: PASS` か見る | `NG テスト …: Result: FAIL …` |
| `requireTests([名前…])` | 最後に回したテストの結果（`.issue-run/test-results/junit.xml`）に、その名前のテストがあって通ったか見る。名前は `it('…')` の文（`describe` の名前を付けた全部でもよい） | `NG テストが無い: …` |
| `mustExist([パス…])` | ファイル・フォルダーがあるか | `NG ある: …` |
| `gitTracked([パス…])` | git が管理しているか（作ったファイルをコミットしたか） | `NG git に入っている: …` |
| `gitClean([パス…], { base })` | 変えていないか（作業ツリーと、`base` を渡せばそのコミットから） | `NG 変えていない: …` |
| `check(条件, '理由')` | その Issue だけの確かめ | `NG 理由` |
| `done()` | ここまでに NG が 1 つでもあれば exit 1、無ければ exit 0 | — |

使い方の詳細は `docs/guides/procedures/node-test-procedure.md`。`scripts/test.mjs` は、テストが 0 件・結果の XML が無い・vitest が無いを全部「合格でない」にする。

### 4.2 その Issue だけの確かめを書く

既存のテストに無いことは、確認コマンドの中に直接書く。**Issue の中に書いたものは Claude が書き換えられない**ので、一番固い。

```js
import { readFileSync, existsSync } from 'node:fs';
import { runTests, requireTests, check, done } from './scripts/issue-run/check-lib.mjs';

// 例: 文書に必要な節がそろっている
const d = 'docs/guides/working/score-validation-design.md';
const t = existsSync(d) ? readFileSync(d, 'utf8') : '';
for (const h of ['## 0. ゴールと合格の条件', '確認コマンド']) check(t.includes(h), `節がある: ${h}`);

// 例: 特定のテストが結果の中にあって通った（名前で 0 件にならないことも見る）
runTests();
requireTests(['マイナスのスコアなら 400 を返す', '整数でないスコアなら 400 を返す']);

done();
```

- 落ちる所は `check(条件, '理由')` で出す。その出力の末尾が Claude に渡り、次に何を直すかの手がかりになる。**途中で止めずに後ろの行まで見て、最後に `done()`。**
- 例の設計書・テストの名前は架空。実在のものに直して書く。
- 試しに作るもの（一時の出力）は `os.tmpdir()` の下か `.issue-run/` の下に作る。git の追跡物を作らない。
- **「直す前と同じ結果」を確かめるとき**は、Issue を書いた時点のコミットを `git show <sha>:<パス>` で取り出して同じ入力で回し、出力を比べる。
- **大文字小文字だけの改名**（`rankings.ts` → `Rankings.ts`）は、Windows と Mac の既定のファイルシステムが区別しない。`git ls-files` の結果で比べる。
- **確認コマンドそのものの誤りで、作る側をどう直しても通らない形になっていないか**を見る。元のリポジトリでは、判定の 1 行が出力先の絶対パスに必ず当たる・試しの入力が空で必ず誤りを出す・変数の名前が空に置き換わって別のファイルを見る、の 3 つで回を使い切った。**後ろの行も、偽の状態（作ったことにした状態）で回して確かめる。**

### 4.3 テストの重さ

- vitest の単体の試験は速い（数秒）。HTTP と DB を通す試験（Workers なら `@cloudflare/vitest-pool-workers`）は、起動に数秒〜十数秒かかる。確認コマンドの中で `runTests()` を何度も呼ばず、1 回回してから `requireTests` で名前を見る。
- **コメントだけの変更**（頭書き・説明）はテストを回さない。「変えたのはコメントの行だけ」を `git diff` で確かめる。
- デプロイ（`wrangler deploy` など）を確認コマンドに入れない（無人の回では断られる）。

### 4.4 変えさせたくないファイルを守る

**確認コマンドに出てくる、git が管理しているファイルは、自動で守られる。** 開始時の中身から変わっていたら（消しても）合格にならない。

確認コマンドで使わないが守りたいファイルは、コメントの行にパスを書けば守られる:

```js
// 守る: test/rankings.test.ts
// 守る: docs/guides/working/score-validation-design.md
import { runTests, done } from './scripts/issue-run/check-lib.mjs';
runTests();
done();
```

- 守れるのは**ファイル単位**。フォルダーを書いても守られない。フォルダーごと変えさせたくないときは、確認コマンドで `gitClean(['migrations/'])` と見る。
- **直させるファイルは、確認コマンドの中で変数を通して指す**（`const src = 'src';` → `` `${src}/rankings.ts` ``）。パスをそのまま書くと自動で守られ、直せなくなる（「直すべきファイルは変数で指す」とコメントを残す）。**注釈の中に書いたパスも守るファイルになる**（`// 守る:` が効くのと同じ仕組み）。`package.json` を直させる Issue なら、`const pkgFile = ['package', 'json'].join('.');` のように名前を分けて組み立て、注釈にも名前をそのまま書かない（rpg-online-cloudflare #1 の下書きで実際に守られてしまい、`--dry-run` の「守るファイル」で気づいた）。
- **変数に入れるのはフォルダーまで**にする。`const d = 'docs/…/x-design.md';` のようにファイルのパスを丸ごと代入しても、そのパスは確認コマンドにそのまま書いてあるので守られる（ファイルがまだ無いうちは守られないが、すでにある文書を直す Issue に写すと直せなくなる。Unity 版を使うリポジトリで、説明書を直す Issue が 4 回とも合格できなかった）。
- **作業で直す必要のあるファイルを「守る」に入れない。** 元のリポジトリでは、旧い名前を消す作業なのに、その名前が残る設計書を守っていて、4 回とも合格できなかった。
- **テストのファイルを守る**のが要。守らないと、Claude がテストの期待値を実装に合わせて直せてしまう。テストそのものを書かせる Issue では、守らずに「既存のテストを消さない・弱めない」を条件に書き、`requireTests` で名前を見る。
- どのファイルが守られるかは `--dry-run` の「守るファイル」に出る。作ったら `--dry-run` の「守るファイル」の行を**切らずに全部読み**、直させるファイルが 1 つも入っていないことを確かめる。

## 5. Issue を書く

GitHub の「New issue」でひな形「Claude に無人で進めさせる」を選ぶ（ひな形が出ないうちは手で書く）。**作った後に、ラベル `claude-run` を付ける。** ひな形では付けない（公開のリポジトリでは、だれでもひな形から Issue を作れるため。付ける前に本文を読む）。

| 欄 | 書くこと | 必須 |
|---|---|---|
| タイトル | 何をするかを1行 | ○ |
| やること | ゴールを1文（2 章）。**90 分 × 4 回で終わる大きさ** | ○ |
| 元の文書 | 設計書・計画書のパスと節 | ○ |
| 合格の条件 | 箇条書き（3 章）＋ ```` ```js ```` の確認コマンド（4 章） | ○（どちらかが無いと起動しない） |
| 前提 | この Issue の前に済んでいるべき Issue（`- #1` のように）。同じ実行の中で前の段が合格すれば、続けて次の段が始まる | 任意 |
| 先に決めておくこと | Claude が迷いそうな点。書かなかった点は Claude が「git で戻せて範囲が小さいほう」を選ぶ | 任意 |
| やらないこと | 範囲の外。見た目の判定・デプロイ・パッケージの追加など | 任意 |

### 5.1 大きさの目安

- 1つの Issue に、確認コマンドで確かめる「終わりの状態」は1つか2つ。
- 「設計書の §4 を全部」ではなく「§4.2 だけ」。
- 元のリポジトリの実測: 設計書を書く Issue は約 30 分、実装の Issue は 8〜17 分。前提でつないでおけば、途中で1件つまずいても後ろは前提待ちで止まるだけ。

### 5.2 段を順につなぐ

大きな作業を段に分けたら、2 段目から先の Issue に「## 前提」で前の段を書き、全部に `claude-run` を付けておく。番号の小さい順に回るので、1 段目が合格すると同じ実行の中で 2 段目が始まる。

- 後の段の確認コマンドが「前の段と同じ結果か」を比べるなら、前の段に比べるための記録を機械で読める形（JSON）で残させる。
- 前の段の Issue の最後に「## 次の段」を書いておくと、後で読むとき流れが分かる（スクリプトは読まない）。
- 設計書を書く Issue の合格の条件に「実装を分けた束（K1・K2…）の一覧と、束ごとの確認コマンドの案」を入れておくと、2 回目以降の Issue がその束を 1 つずつ指せる。テストの名前の表では、束は印の文（「（K2）」など）に混ぜず**「束」の列**に書かせる（見本は 6.2。列の値で絞れば、印の書き方の揺れを確認コマンドで吸わずに済む）。
- 人が手でやるもの（本番への配備・別の PC での確認など）も Issue にしてよいが、`claude-run` を付けない。

## 6. 例

### 6.1 小さい — バグを直す

````
タイトル: マイナスのスコアが登録できてしまう

## やること
マイナスのスコアを送ったら 400 を返し、ランキングに載せないようにする。

## 元の文書
docs/api-contract.md の POST /v1/rankings/boss-score

## 合格の条件
- マイナスのスコアを送ると 400 が返る（テスト「マイナスのスコアなら 400 を返す」）
- 既存のテストが全部通る

```js
// 守る: test/rankings.test.ts
import { runTests, requireTests, done } from './scripts/issue-run/check-lib.mjs';
runTests();
requireTests(['マイナスのスコアなら 400 を返す']);
done();
```

## やらないこと
- 認証の追加・デプロイ
````

テスト「マイナスのスコアなら 400 を返す」はユーザーが先に書いて（または Claude に別の Issue で書かせて）コミットしておく。守るファイルに入っているので、Claude は実装の側を直すしかない。

### 6.2 大きい・1回目 — 設計書を書かせる

````
タイトル: スコア投稿の検証の設計書を書く

## やること
スコア投稿の検証（範囲・型・ゲーム ID・連投）の設計書を、design-cycle の形で書く。

## 元の文書
.claude/skills/design-cycle/SKILL.md（設計書の形）
docs/03-roadmap.md の「優先的にテストする失敗ケース」

## 合格の条件
- 設計書が docs/guides/working/score-validation-design.md にある
- §0 にゴール・合格の条件の表・実装の Issue に使う確認コマンドの案がある
- テストの名前の一覧の表があり、見出しの行が `| 束 | テストの名前 | 何を確かめるか |` で始まる（束は「束」の列に書き、名前の文に混ぜない。名前はバッククォートで囲む）

```js
import { readFileSync, existsSync } from 'node:fs';
import { check, done } from './scripts/issue-run/check-lib.mjs';
const dir = 'docs/guides/working';   // 書かせる文書はフォルダーを変数に入れて組み立てる
const d = `${dir}/score-validation-design.md`;
const t = existsSync(d) ? readFileSync(d, 'utf8') : '';
check(t.length > 0, '設計書がある');
for (const h of ['## 0.', 'ゴール', '合格の条件', '確認コマンド', 'テストの名前']) check(t.includes(h), `ある: ${h}`);
check(/^\| *束 *\| *テストの名前 *\| *何を確かめるか *\|/m.test(t), 'テストの名前の表に「束」の列がある');
done();
```

## やらないこと
- 実装（2回目の Issue でやる）
````

設計書のテストの名前の表は、この形にさせる（束は「束」の列に 1 つだけ書く。名前はバッククォートで囲む）。下は表の頭の数行。

| 束 | テストの名前 | 何を確かめるか |
|---|---|---|
| K1 | `マイナスのスコアなら 400 を返す` | 範囲の下限 |
| K1 | `整数でないスコアなら 400 を返す` | 型 |
| K2 | `知らないゲーム ID なら 404 を返す` | ゲーム ID |

### 6.3 大きい・2回目 — 実装する

````
タイトル: スコア投稿の検証を実装する（設計書の束 K2）

## 前提
- #1

## やること
設計書の束 K2 を設計書どおりに実装し、束 K2 の合格の条件のうち機械で測れるものを全部満たす。

## 元の文書
docs/guides/working/score-validation-design.md の束 K2

## 合格の条件
- 設計書のテストの名前の表で「束」の列が K2 の行のテスト（12 本）が全部ある・通る
- 既存のテストが全部通る

```js
// 守る: docs/guides/working/score-validation-design.md
import { readFileSync } from 'node:fs';
import { runTests, requireTests, check, done } from './scripts/issue-run/check-lib.mjs';
// テストの名前は設計書の表から読む（Issue に写さない。表が正）。「束」の列の値で行を絞る
const t = readFileSync('docs/guides/working/score-validation-design.md', 'utf8');
const rows = [...t.matchAll(/^\| *([^|`]+?) *\| *`([^`]+)` *\|/gm)];
const names = rows.filter((m) => m[1] === 'K2').map((m) => m[2]);
// 本数は Issue を書く人が設計書の表を数えて書く（12 は設計書の束 K2 の行の数。requireTests は渡された名前しか見ないので、読めなかった名前は確かめられない）
check(names.length === 12, '表から読めた束 K2 の名前が 12 本');
runTests();
requireTests(names);
done();
```

## やらないこと
- 使い心地の判定（後でユーザーが触って決める）
````

設計書を「守る」に入れると、Claude は実装の都合で設計書を書き換えられない。設計を変えたくなったら合格にならず、報告の「やらなかったこと」に理由が残る（設計の直しはユーザーが決める）。

## 7. 札を付ける前の確かめ

- [ ] やることが1文で、90 分 × 4 回で終わる大きさ
- [ ] 元の文書のパスが実在する
- [ ] 合格の条件の箇条書きが、全部「機械で測れる」
- [ ] 箇条書きの1行ずつが、確認コマンドのどこかで確かめられる
- [ ] 確認コマンドを**自分で一度実行して**（直下で `node --input-type=module < 下書き.mjs`）、今は落ちる（まだできていない）ことを見た。最初から通るなら、ゴールが書けていない
- [ ] 落ちたときの `NG` の理由が「まだ作っていないから」になっている（確認コマンド自身の誤りで落ちていない）。後ろの行も偽の状態で回した
- [ ] 変えさせたくないファイル（特にテストのファイル）が「守る」に入っている
- [ ] 見た目・使い心地など本人の判断が要るものは「やらないこと」に入っている
- [ ] `node scripts/issue-run/issue-run.mjs --issue <番号> --dry-run` で、条件の行数と守るファイルが期待どおり

## 8. 終わった後の確認

1. `docs/reports/YYYY/MM/DD/NN-issue-run.md`（まとめ。合格しなかったものが先）
2. 合格した Issue のコメント: 判定表・**選んだこと（Claude が自分で決めた点と戻し方）**・やらなかったこと
   - 選んだことが違っていたら、コメントの戻し方で戻し、「先に決めておくこと」に正しい決定を書いて、ラベル `claude-done` を外す（次の回でやり直す）
   - 良ければ閉じて push する
3. 合格しなかった Issue（`claude-failed`）: コメントの理由を見る
   - 合格の条件か確認コマンドが無い → 書き足す（確認コマンドの塊の言語が `js` になっているかも見る）
   - 回数切れ → 大きすぎる。分ける
   - 守るファイルを変えようとした → 設計か確認コマンドが実情に合っていない。直す
   - 「最後の返答」が `You've hit your session limit`・`ENOTFOUND` など → 中身の不合格ではない。条件を変えずに `claude-failed` を外して出し直す
   - 権限で断られて 1 か所だけ書けなかった → 報告に用意された中身を手で入れてコミットし、出し直すか手で閉じる
   - 直したらラベル `claude-failed` を外す。**何を直したか・条件を変えたかをコメントに残す**（「## 対応（日時・ユーザーのセッションから）」に、直したこと・「本文の合格の条件は変えない」・次にどうするか）
4. 閉じるときは「合格（claude-done）を確認して閉じる（YYYY-MM-DD ユーザー指示）」とコメントしてから閉じる
5. 「未採用の改善」に良いものがあれば、新しい Issue にする（自動では仕事にならない）
