# ファイルヘッダー Skill（TypeScript / JavaScript 用）

TypeScript・JavaScript のソースファイルの先頭に「このファイルは何か」の概要コメントを付ける。

## トリガー

| ユーザーの表現 | 動作 |
|---|---|
| "ヘッダーコメントを追加して" | 指定範囲のファイルに概要ヘッダーを付ける |
| "ファイルの概要を書いて" | 同上 |
| "このファイルにヘッダーを" | 単一ファイル |
| 新規 `.ts`・`.mjs` を作るとき | **常に**付ける（言われなくてよい） |

## 対象と対象外

**対象:** `src/**/*.ts`・`scripts/**/*.mjs`・テストのファイル（自作のもの）

**対象外（触らない）:**
- `node_modules/` の中・外から取ってきたコード
- 自動生成されたコード（型の生成物・`*.d.ts` の生成物など。作り直すと消える）
- JSON・SQL（用途は名前と中身で分かる。`migrations/` の SQL は先頭に 1 行の `--` コメントだけなら可）

### まず既存の説明を数える

```bash
# 先頭 20 行に 3 行以上のコメントがあるか＝説明の有無
for f in $(git ls-files 'src/*.ts' 'scripts/*.mjs'); do
  n=$(head -20 "$f" | grep -cE '^\s*(//|/\*|\*)')
  [ "$n" -ge 3 ] || echo "説明なし: $f"
done
```

作業前に数え、対象を確定してから始める（元のリポジトリで「先頭行がコメントか」で数えて誤報告した）。
既に十分な説明があるファイルは触らない。他人（別モデル・人間）が書いた説明に自分の署名を足さない。書き直すのは、説明が**間違っている**ときだけ。

## 書式

**位置は「ファイルの一番上」。** `#!/usr/bin/env node` があればその次、`import` より前。JSDoc（関数の説明）とは別物で、両方あってよい。

```ts
// <ファイル名> — <1行で何か>。
//
// <2〜5行の補足: 役割 / 他ファイルとの関係 / 読むときの注意>
//
// 概要記述: Claude {現在のモデル名} — {YYYY-MM-DD}
import { ... } from '...';
```

実例:

```ts
// rankings.ts — ランキングの取得と投稿の検証（HTTP と D1 に触らない、ふつうの関数）。
//
// worker.ts が要求を受けてここを呼び、D1 への読み書きは db.ts が持つ。スコアの上限と
// 検証の決まりは limits.ts の定数 1 か所。単体の試験で検証の式を直接確かめる。
//
// 概要記述: Claude Opus 5.5 — 2026-10-23
import { LIMITS } from './limits';
```

### 署名について

**署名するのは「ファイルの作者」ではなく「この概要コメントを書いた主体」。** `概要記述:` という語を使うのはそのため。

- 概要を**書き直した**ときは日付とモデル名を更新する
- コードだけ直して概要が変わらないなら署名はそのまま

## 内容のルール

**書くこと:** そのファイルが何を担当するか（1行で言い切る）・他ファイルとの関係（誰が呼ぶ / 誰を呼ぶ / どこに状態があるか）・読むときにハマる点（非同期の順番に頼っている・環境変数が要る・Workers の実行環境でしか動かない 等）

**書かないこと:** コードを日本語に置き換えただけの説明・関数の一覧・変更履歴（git が持っている）・TODO（該当行に書く）

## 手順

1. **ファイルを最後まで読む。** 読まずに概要を書かない
2. 既存の説明コメントを探し、あれば流用・移動する
3. ヘッダーを先頭に挿入する
4. `git diff` で**コメント以外が混ざっていないこと**を確かめる。コメントだけの変更なら型の確かめは要らない
