# ファイルヘッダー Skill（Unity / KaedeScapeBuii 用）

C# のソースファイルの先頭に「このファイルは何か」の概要コメントを付ける。kaedevn（UE）の file-header と同じ考え方。

## トリガー

| ユーザーの表現 | 動作 |
|---|---|
| "ヘッダーコメントを追加して" | 指定範囲のファイルに概要ヘッダーを付ける |
| "ファイルの概要を書いて" | 同上 |
| "このファイルにヘッダーを" | 単一ファイル |
| 新規 `.cs` を作るとき | **常に**付ける（言われなくてよい） |

## 対象と対象外

**対象:** `Assets/**/*.cs`（自作のもの）

**対象外（触らない）:**
- `Packages/` の中・`Library/PackageCache/`・Asset Store などから入れた外部のコード
- 自動生成されたコード（Input System の `*.inputactions` から生成した C# クラス など。作り直すと消える）
- `*.asmdef`（JSON。用途は名前で分かる）

### まず既存の説明を数える

```bash
# 先頭 20 行に 3 行以上のコメントがあるか＝説明の有無
for f in $(git ls-files 'Assets/*.cs'); do
  n=$(head -20 "$f" | grep -cE '^\s*(//|/\*|\*)')
  [ "$n" -ge 3 ] || echo "説明なし: $f"
done
```

作業前に数え、対象を確定してから始める（kaedevn で「先頭行がコメントか」で数えて誤報告した）。
既に十分な説明があるファイルは触らない。他人（別モデル・人間）が書いた説明に自分の署名を足さない。書き直すのは、説明が**間違っている**ときだけ。

## 書式

**位置は「ファイルの一番上」。** `using` より前。`///` の XML ドキュメントコメント（クラスやメソッドの説明）とは別物で、両方あってよい。

```csharp
// <ファイル名> — <1行で何か>。
//
// <2〜5行の補足: 役割 / 他ファイルとの関係 / 読むときの注意>
//
// 概要記述: Claude {現在のモデル名} — {YYYY-MM-DD}
using UnityEngine;
```

実例:

```csharp
// PlayerMotor.cs — プレイヤーの移動と接地の判定（MonoBehaviour を持たないふつうの C#）。
//
// 入力は PlayerInputBridge が Input System の Move/Jump から渡す。物理は持たず、
// 次のフレームの速度を返すだけ。EditMode のテストで速度の式を直接確かめる。
//
// 概要記述: Claude Opus 5.5 — 2026-10-22
using UnityEngine;
```

### 署名について

**署名するのは「ファイルの作者」ではなく「この概要コメントを書いた主体」。** `概要記述:` という語を使うのはそのため。

- 概要を**書き直した**ときは日付とモデル名を更新する
- コードだけ直して概要が変わらないなら署名はそのまま

## 内容のルール

**書くこと:** そのファイルが何を担当するか（1行で言い切る）・他ファイルとの関係（誰が呼ぶ / 誰を呼ぶ / どこに状態があるか）・読むときにハマる点（Unity の呼ばれる順〔Awake/OnEnable/Start〕に頼っている・シリアライズされる欄の名前を変えると値が消える 等）

**書かないこと:** コードを日本語に置き換えただけの説明・関数の一覧・変更履歴（git が持っている）・TODO（該当行に書く）

## 手順

1. **ファイルを最後まで読む。** 読まずに概要を書かない
2. 既存の説明コメントを探し、あれば流用・移動する
3. ヘッダーを先頭に挿入する
4. `git diff` で**コメント以外が混ざっていないこと**を確かめる。コメントだけの変更ならコンパイルは要らない
