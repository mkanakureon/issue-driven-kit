**Mac**（Node 版だけ）

```bash

brew install gh
# Node.js 22.14.0 は公式の .pkg（https://nodejs.org/dist/v22.14.0/node-v22.14.0.pkg）で入れる（PATH が自動で通る）
npm install -g npm@11.6.2
```

Node.js は**公式の `.pkg` を推します**。入れると `/usr/local/bin` に `node` と `npm` が入り、PATH を足す手順が要りません。

tar.gz を広げて入れたとき・nvm などで入れたときは、PATH が通っていません。**人が** `~/.zprofile` に次の 1 行を足し、新しいターミナルで `node --version` が `v22.14.0` になるのを見ます（`<入れた所>` は広げたフォルダー）。

```bash

```

この追記は Claude Code に頼みません。`~/.zprofile` は人のシェルの設定のファイルなので、Claude Code の auto mode は追記を断ります（断るのが正しい動きです）。

入れるのを Claude Code に頼むこともできます（キットの元の作者は「pwshを入れて」「いれて」と入力しました）。

### 1.3 ログイン（人がする）

GitHub のログインは、人が `!` を付けて入力します（`!` で始めると、その窓で人のコマンドとして実行されます）。

```text

```

無人の回用の長いトークンは、**Claude Code の外のターミナル**（Windows はもう 1 つの PowerShell、Mac はターミナル）で作ります。`!` を付けて Claude Code の中で回すと、端末（TTY）が無く標準入力が空のまま動くので、ブラウザで承認した後で止まり、トークンが出ません。

```text

```

出た値は秘密の値です。**会話に貼らない**で、自分で環境変数 `CLAUDE_CODE_OAUTH_TOKEN` に入れます。無人の回が長く動く途中でログインが切れるのを防ぎます。

**Windows**

ユーザーの環境変数に入れます（「設定 > システム > バージョン情報 > システムの詳細設定 > 環境変数」の「ユーザー環境変数」）。すでに開いている窓には渡りません。無人の回は起動した窓の環境変数を子へ渡すので、入れた後に開いた新しい窓で起動します。

**Mac**

`~/.zprofile` に `export CLAUDE_CODE_OAUTH_TOKEN=<値>` の 1 行を足します。PATH と長いトークンは、ターミナルの新しい窓（ログインのシェル）が読む `~/.zprofile` にそろえます。

## 手順 4：キットを入れる

自分のリポジトリのフォルダーで Claude Code を起動し、こう入力します。**キットの導入ガイドを読ませて、版を名指しする**のがこつです。

**Node 版**

```text
<キット> の導入ガイド（キットの README から辿れる）を読んで、
このリポジトリに Node 版を入れて。まず --dry-run で、写すファイルと、ぶつかるファイルを見せて
```

**Unity 版**

```text
<キット> の導入ガイドを読んで、このリポジトリに Unity 版を入れて。まず -DryRun で、写すファイルと、ぶつかるファイルを見せて
```

**Claude Code がすること**

| 順 | すること |
|---|---|
| 1 | 入れる脚本を `--dry-run`（Unity 版は `-DryRun`）で実行し、写すファイルの一覧と、既にあるファイルとぶつかる所を見せる。ここで止まる |
| 2 | 人が「入れて」と入力したら、入れる脚本を本番で実行する。既にあるファイルは上書きしない |
| 3 | **Node 版だけ**：vitest（と、Cloudflare Workers のプロジェクトなら `@cloudflare/vitest-plugin`。旧 `@cloudflare/vitest-pool-workers` は非推奨）を `devDependencies` に足し、`npm test` が `scripts/test.mjs` を呼ぶようにする。`package.json` の `engines` と `.nvmrc` に Node.js の版を書く。版の組み合わせは公式の案内で確かめて固定する（Mac では vitest 5.0.3・`@cloudflare/vitest-plugin` 1.4.0 で通った。入れる脚本はパッケージを足さない） |
| 4 | `CLAUDE.md` の「プロジェクト」「コマンド」を、このリポジトリに合わせて書く（何を作るか・使う技術・テストの打ち方）。入れる脚本が `CLAUDE.kit.md` などを横に置いたときは、先にその中身を既にある物に足して、横に置いた物を消す |

Cloudflare Workers のプロジェクトでは、`vitest.config.ts` で `@cloudflare/vitest-plugin` の `cloudflareTest` を使い、`wrangler.jsonc` を読ませます（Cloudflare の公式の案内「Write your first test」の書き方）。

```ts
import { cloudflareTest } from "@cloudflare/vitest-plugin";
import { defineConfig } from "vitest/config";

export default defineConfig({
  plugins: [
    cloudflareTest({
      wrangler: { configPath: "./wrangler.jsonc" },
    }),
  ],
});
```

`wrangler.jsonc` の `compatibility_date` が新しすぎるとテストが 1 本も回りません（「[困ったとき](#困ったとき)」）。

入れる脚本は、ファイルを写すほかに、人の入力の置き場と記録の置き場（Node 版 `docs/inspecs/`・`docs/reports/`、Unity 版 `Docs/InSpecs/`・`Docs/Reports/`）を無ければ作り（中に `.gitkeep`）、`.issue-kit/version` を書きます。Node 版は `.gitignore` に `.issue-run/` の 1 行を足します。どちらも最後の行が `Result: PASS`／`Result: FAIL` です。

| 引数（Node 版／Unity 版） | 動き |
|---|---|
| `--target <パス>`／`-Target <パス>` | 入れる先（git の作業場所の直下）。直下でなければ止まる |
| `--dry-run`／`-DryRun` | 写すファイルと、ぶつかるファイルを出すだけ。何も書かない（`Result: PASS (DryRun・何も書いていない)`） |
| （なし） | 初めて入れる。既にあるファイルは上書きしない。利用先が手を入れる物（Node 版 `CLAUDE.md`、Unity 版 `CLAUDE.md`・`.gitignore`・`.gitattributes`）が既にあれば、それは残し、キットの物を `CLAUDE.kit.md`・`.gitignore.kit` のように横に置いて残りを入れる（`Result: PASS (… 件を写した・横に置いた N 件 …)`）。ほかに中身の違うファイルがあれば、何も書かずに一覧を出して `Result: FAIL (ぶつかる N 件)` |
| `--update`／`-Update` | 入っている版を上げる。利用先が手を入れるファイル（`CLAUDE.md` など）は上書きせずに残し、その一覧と最後の行の「残した N 件」で知らせる（`Result: PASS (… 件を写した・残した N 件 …)`）。残した物はキットの物と比べて要る所を足す（Claude Code に頼める）。ほかのファイルは、手を入れていても上げる（上書きする） |

```text
入れて
```

自分でコマンドを実行してもかまいません。

```text

node <キット>/editions/node/install.mjs --target .
```

## 手順 5：確かめる

### 5.1 テストの入口

テストの入口は、無人の回が合否を読む唯一の口です。**3 つの場合を必ず確かめます。**

```text
テストの入口を、全部・0 件（無い名前で絞る）・わざと落とすテストを 1 本足す、の 3 つで回して、
最後の Result: 行と終了コードを見せて。わざと落とすテストは最後に消して
```

| 回し方 | 期待する最後の行 | 終了コード |
|---|---|---|
| 全部 | `Result: PASS <件数>` | 0 |
| 0 件 | `Result: FAIL … 0/0` | 1 |
| わざと落とす | `Result: FAIL` | 1 |

### 5.2 点検と DryRun

```text
issue-run の点検を回して
```

```text
issue-run を DryRun で回して
```

点検は 1 行ずつ `OK`／`WARN`／`NG` を出し、最後の行が `Result: PASS  WARN <数>`（NG 0・終了コード 0）か `Result: FAIL  NG <数>・WARN <数>`（終了コード 1）です。`WARN` は通りますが、読んで要るものは直します。

| 点検 | 通る状態 |
|---|---|
| 道具（node・npm・git・gh・claude）・gh のログイン・`origin`・ラベル・部品のファイル | `OK` |
| 禁止の設定 | `OK   設定: deny <数> 個・Stop hook（node）…`（裸の `CLAUDE.md` の禁止が無い） |
| テストの仕組み（Node 版） | `vitest` が `devDependencies` にあり、`node_modules` に入っている。`npm test` が `scripts/test.mjs` を呼ぶ |
| テストの入口（Node 版。`--run-tests` を付けたときだけ） | `OK   テスト: Result: PASS …` |
| キットの版（Node 版） | 入っている版がキットの最新なら `OK`、古ければ `WARN`（手順 8 で新しくする） |
| 長期トークン | `CLAUDE_CODE_OAUTH_TOKEN` が無ければ `WARN`（手順 1.3） |
| 眠らせない（Node 版） | Mac は `OK`（`caffeinate` を無人の回が使う）。Windows は電源の設定を知らせる `WARN` |
| DryRun | `[時刻] 対象 <数> 件: …` を出して終了コード 0（Issue がまだ無ければ「対象 0 件」） |

コマンドで回すなら：

```text
node scripts/issue-run/doctor.mjs
node scripts/issue-run/doctor.mjs --run-tests
node scripts/issue-run/issue-run.mjs --dry-run
```

```powershell
pwsh -NoProfile -File Scripts/issue-run-doctor.ps1
pwsh Scripts\issue-run.ps1 -DryRun
```

## 手順 6：最初の Issue を回す

最初は**文書を書かせる Issue** にします。合格の条件が「章・字数・リンク先が実在」のように機械で測れ、仕組みの確かめと中身の失敗が混ざりません。

| 段 | 入力するプロンプト | Claude Code がすること |
|---|---|---|
| 1 | `<作りたい物の説明>。上記を整理して基本設計書にして、その後どこから Issue 駆動にするか検討して` | 基本設計書と、決めること（推しの案つき） |
| 2 | `おすすめで決めて` | 推しの案で決める |
| 3 | `詳細設計を書かせる Issue にして` | Issue の下書き。確認コマンドを回して、いま落ちることを確かめる |
| 4 | `コミットしてpushしてから作って` | コミット → push → GitHub に Issue を作る |
| 5 | （**人が別の窓で**無人の回を起動する。下のコマンド）→ `issue-run を起動した` | 読むだけで様子を見る |
| 6 | `様子見て` … `終わったみたい` | 合否・時間・無人の回が自分で決めたことを報告 |
| 7 | `コミットしてpushして` → `doneはcloseして` | まとめを入れて push、合格の Issue を閉じる |

無人の回の起動（別の窓で、自分のリポジトリのフォルダーで）：

```text
node scripts/issue-run/issue-run.mjs
```

```powershell
pwsh Scripts\issue-run.ps1
```

多くの段で、次に入力するプロンプトが入力欄に灰色で出ます。合っていれば Tab → Enter で送れます。外への書き込み（「作って」「コミットしてpushして」「doneはcloseして」）は、下書きや結果を読んでから送ってください。

### 6.1 長く回す（放っておくとき）

無人の回は、札（`claude-run`）の付いた Issue を 1 件ずつ順に回し、合格するまで同じ会話を再開します。1 件の時間・再開の回数・1 回に回す件数・利用上限に当たったときの待ち方には上限があり、**既定の値と変え方は入れた先の `docs/guides/working/issue-run.md` の「起動」**にあります（キットの中では [`issue-run.md`](../../editions/node/files/docs/guides/working/issue-run.md)）。値はそこと脚本の既定の値が正なので、このガイドには写しません。

| 知りたいこと | どうなるか |
|---|---|
| 合格しなかった | その Issue に `claude-failed` の札が付き、次の Issue へ進みます。直し方は、入れた先の `docs/guides/procedures/issue-goal-setting.md` の 8 章 |
| 途中で止める | 窓を閉じるか `Ctrl+C` で止めます。回していた Issue には実行中の札 `claude-working` が残り、その Issue は対象から外れます。**次の起動で対象が 1 件以上あれば、前回の実行中の札が外れて対象に戻ります**（窓に「前回の実行中の札を外した」と出ます。ほかの worktree で動いている回の分は外しません）。止めた Issue のほかに対象が無いと「対象 0 件」で終わって札は残るので、そのときは `--issue <番号>` で 1 件だけ起動します（札を見ずに回し、残った札も外します） |
| 中身のログ | `.issue-run/logs/<日時>/`（Issue ごとの指示・会話の結果・確認コマンドの出力） |
| 回の履歴 | `.issue-run/logs/runs.log`（回ごとに 1 行。対象 0 件の回も残ります） |
| まとめ | `docs/reports/YYYY/MM/DD/NN-issue-run.md`（合格しなかった → 合格した、の順。コミットして残します） |
| 終わりの知らせ | 1 件以上回した回の終わりに、窓にベルと結果の 1 行が出ます（Mac は通知センターにも） |

**Issue は、そのリポジトリに書き込みの権限（`write`・`maintain`・`admin`）のある人が書きます。** 無人の回は、権限の無い人が作った Issue を対象から外し、DryRun（`--dry-run`）と本番の最初の行に「外した」と番号・理由を出します。チームで使って「対象 0 件」になったら、まずここを見ます（決まりの正は仕様 [`issue-run-spec.md`](../spec/issue-run-spec.md) の 1.2）。

Unity 版は置き場が違います（ログは `Logs/IssueRun/`、まとめは `Docs/Reports/`）。`runs.log`・終わりの知らせ・書き込みの権限の確かめは、Unity 版ではまだ入っていません（仕様の版の違いの表）。

## 困ったとき

| 症状 | 原因 | 直し方 |
|---|---|---|
| 入れる脚本が `CLAUDE.kit.md` を横に置いた | 既に `CLAUDE.md` がある（Unity 版は `.gitignore`・`.gitattributes` も同じ。`.gitignore.kit` などになる） | Claude Code に頼む（「CLAUDE.kit.md の原則と入口を、既にある CLAUDE.md に足して、CLAUDE.kit.md を消して」） |
| 入れる脚本が「ぶつかる」と止まった（何も書いていない） | 利用先が手を入れる物でないファイルで、同じ名前・違う中身の物がある（例：既にある `scripts/test.mjs`） | 一覧を見て、そのファイルをどうするか Claude Code と決める（名前を変えて退ける・キットの物に足す形にする）。そのあと入れ直す |
| テストの入口が 0 件で PASS になる | テストの入口の作りの誤り | 5.1 の 3 つで確かめ直す。PASS になるなら直してから先に進む |
| `gh` が見つからない（Windows） | 入れた直後のシェルに PATH が通っていない | 新しい窓を開く |
| 点検で「裸の CLAUDE.md の禁止」 | 禁止の設定に `Edit(CLAUDE.md)` がある | `//{{REPO}}/CLAUDE.md` の形にする（キットの設定はそうなっている） |
| 無人の回が数分で 4 回を使い切った | ネットの切断（`ENOTFOUND` など） | 回線を確かめ、Issue のラベルを `claude-run` に戻して出し直す（「出し直して」） |
| 実装の Issue が全部「設定を変えた」で落ちる | テストを初めて回したときにツールがファイルを作った | 実装の Issue を作る前に確認コマンドを 1 回回し、増えたファイルを先にコミットする |
| Windows で無人の回の途中で止まった | PC が眠った・再起動した | 「設定 > システム > 電源とバッテリー」で、電源につないでいる間は眠らないようにする。あわせて、蓋を閉じたときの動き（「蓋を閉じたときの動作」が「スリープ」になっていないか）と、Windows Update の再起動の時間帯（「アクティブ時間」に回す時間が入っているか）を見る（どちらも実測していないので、見る所として書いています） |
| Mac で日本語が化ける・コマンドが見つからない | シェルの設定 | `node --version`・`gh --version`・`claude --version` が新しいターミナルで出るか確かめる |
| Workers の試験が `ERR_RUNTIME_FAILURE` で 1 本も回らず、テストの入口が `Result: FAIL (0/1)` になる | `@cloudflare/vitest-plugin` の workerd が受け付ける `compatibility_date` には上限がある（1.4.0 は 2026-10-13）。`wrangler.jsonc` の `compatibility_date` がそれより新しい（今日の日付など） | `wrangler.jsonc` の `compatibility_date` を上限以下の日付にする。上限は vitest-plugin の版ごとに違うので、入れた版で確かめる |
