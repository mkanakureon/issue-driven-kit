## やること

Web アプリ・業務アプリを作るチームが、生成AIに慣れていなくても自社の案件に Issue 駆動を試せるように、初心者向けのガイド `Docs/Guides/Manuals/issue-driven-guide-for-teams.md` の骨組みと 0〜6 章（考え方・準備・合格の条件・確認コマンド）を書く（段 1/3）。

## 元の文書

- `README.md`（言葉の説明・なぜ要るか・全体の流れ）
- `Docs/Reports/2026/10/22/02-kaedevn-issue-run-success-case.md`（数字・なぜ成功したか・Issue の書き方のこつ）
- `Docs/Reports/2026/10/22/03-issue-driven-history.md`（失敗から規則を積んだ過程）
- `Docs/Reports/2026/10/22/04-kaedevn-issue-run-build-history.md`（AI 向けの CLI・確認コマンドの入口）
- `Docs/Reports/2026/10/22/05-kaedevn-monorepo-roots.md`（それより前の試み）
- `Docs/Guides/Working/issue-driven-development.md`・`Docs/Guides/Procedures/issue-goal-setting.md`（いまの仕組みと Issue の書き方の正）

## 合格の条件

- ガイドが `Docs/Guides/Manuals/issue-driven-guide-for-teams.md` にあり、見出し 1（`# `）が 1 つだけ
- 次の 7 章があり、どれも 2,000 字以上: `## 0.` はじめに（読む人・読み方・作者の経験）／`## 1.` Issue 駆動とは／`## 2.` なぜ要るか（AI に任せたときの困りごと）／`## 3.` 全体の流れ（Mermaid の図）／`## 4.` 始める前の準備（道具・リポジトリ・権限・安全）／`## 5.` 合格の条件の決め方／`## 6.` 確認コマンドの書き方（Web アプリと業務アプリの例）
- 全体で 18,000 字以上
- 「確認コマンド」「合格の条件」「npm test」「pytest」の語があり、Mermaid の図が 1 つ以上ある
- 文書だけの Issue: `Assets/`・`Scripts/`・`ProjectSettings/`・`Packages/` を変えない
- 元の文書（下の「守る」）を変えない

```pwsh
[Console]::OutputEncoding = [System.Text.Encoding]::UTF8
# 守る: Docs/Reports/2026/10/22/02-kaedevn-issue-run-success-case.md
# 守る: Docs/Reports/2026/10/22/03-issue-driven-history.md
# 守る: Docs/Reports/2026/10/22/04-kaedevn-issue-run-build-history.md
# 守る: Docs/Reports/2026/10/22/05-kaedevn-monorepo-roots.md
# 守る: Docs/Guides/Procedures/issue-goal-setting.md
# 守る: Docs/Guides/Working/issue-driven-development.md
# （書かせる文書は変数で指す。そのまま書くと守るファイルになって書けない）
$dir = 'Docs/Guides/Manuals'; $d = "$dir/issue-driven-guide-for-teams.md"
if (-not (Test-Path $d)) { Write-Host "まだ無い: $d"; exit 1 }
$t = Get-Content $d -Raw -Encoding utf8
# コードブロックの中の行頭の # は見出しとして数えない（Issue の例・ひな形・コマンドのコメントを章の切れ目と取り違えない）。長さは変えない。'```' の中に '```pwsh' を入れた二重のブロックも、開いた記号の長さで閉じを見る
$fence = ''
$s = (($t -split "`n") | ForEach-Object {
        if ($fence) { if ($_ -match ('^' + $fence + '`*\s*$')) { $fence = ''; $_ } else { $_ -replace '^#', ' ' } }
        elseif ($_ -match '^(`{3,})') { $fence = $Matches[1]; $_ }
        else { $_ }
    }) -join "`n"

$h1 = ([regex]::Matches($s, '(?m)^# ')).Count
if ($h1 -ne 1) { Write-Host "見出し 1 が $h1 個（1 個にする）"; exit 1 }
foreach ($n in 0..6) {
    $m = [regex]::Match($s, "(?ms)^## $n\. .*?(?=^## |\z)")
    if (-not $m.Success) { Write-Host "章が無い: ## $n."; exit 1 }
    if ($m.Value.Length -lt 2000) { Write-Host "## $n. が短い: $($m.Value.Length) 字（2,000 字以上）"; exit 1 }
}
if ($t.Length -lt 18000) { Write-Host "全体が短い: $($t.Length) 字（18,000 字以上）"; exit 1 }
foreach ($w in '確認コマンド', '合格の条件', 'npm test', 'pytest') { if ($t -notmatch [regex]::Escape($w)) { Write-Host "無い語: $w"; exit 1 } }
if (([regex]::Matches($t, '(?m)^```mermaid')).Count -lt 1) { Write-Host 'Mermaid の図が無い'; exit 1 }
if (git status --porcelain -- Assets Scripts ProjectSettings Packages) { Write-Host 'コード・設定を変えている（文書だけの Issue）'; exit 1 }
Write-Host 'OK'
exit 0
```

## 先に決めておくこと

- **読む人**: テストユーザーの会社の開発者・PM・発注側の人。生成AIを使った開発に慣れていない人を含む。**作るものは Web アプリ・業務アプリ**（UE や Unity のゲームではない）。だから一般的な言葉と例に寄せる。ゲームエンジンの話は「元の事例」として触れるだけにする。
- **作者の経験**（0 章に書く）: 作者は 1 年以上、生成AIを使って開発してきた。kaedevn-monorepo（2026-02〜）より前にも試作が多数あり、monorepo もそれらの試作の経験がもとになっている。その上に kaedevn（2026-06〜）で Issue 駆動を形にし、8 日間で 105 件を合格させた（数字は 02 から引く）。
- **書き方**: 日本語・です・ます調。専門の言葉は初めて出たときに短く説明する。たとえ（「腕はいいが早合点する新人」など）を使ってよい。
- **例のコマンド**（`npm test`・`pytest`・`curl` など）は一般的な形で書き、「自社のコマンドに置き換える」と書く。架空の製品名・社名を作らない。
- **数字と事実**は元の文書から引き、どの文書から引いたかを書く。元の文書に無い数字を作らない。
- 社名・個人名・メールアドレス・ローカルのパスを書かない。
- 7 章以降は次の段の Issue で書く。この段では、0〜6 章の後ろに「7 章以降は次の段で書く」とだけ書いてよい。

## やらないこと

- 元の文書の書き換え
- 7 章以降・付録（次の段）
