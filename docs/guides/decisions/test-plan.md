# テスト計画（Test Plan）— 正・1か所

**これが正。** テストレベル・合格基準・開始／終了基準・中断基準・欠陥管理は、ここ以外に定義しない。CLAUDE.md・スキル・手順書はここを参照するだけで写さない。
構成は IEEE 829 / ISO/IEC/IEEE 29119-3 の項目に、用語は ISTQB 用語集に合わせる。Issue 駆動キット（Node 版）の骨組み。作るものが決まったら §1・§2・§4 を書き足す。

## 0. 用語（左の語だけ使う）

| 用語 | 英語 | この計画での意味 | 使わない語 |
| --- | --- | --- | --- |
| **テスト対象** | test item | `src/`・`migrations/`・`scripts/`（テストのファイルを除く）・`package.json` | 中身・本体 |
| **版** | build | テスト対象のコミット。結果は版に属する | 最新・現在版 |
| **テストレベル** | test level | L1 単体／L2 結合（HTTP・DB を通す）／L3 受け入れ（人間）（§3） | 内部・外部 |
| **回帰テスト** | regression testing | 今あるテストを今の版へ流す（`node scripts/test.mjs`） | 全テスト |
| **確認テスト** | confirmation testing | 直した欠陥を、同じ開始状態・操作で再現し、期待どおりになったことを見る。テストの 1 本として書く | 再現確認 |
| **合格基準** | pass/fail criteria | 1つでも赤ならそのレベルは終わらない | 受け入れ条件・必須 |
| **メトリクス** | test metrics | 測って残す。合否に入れない（実行時間・応答時間 など） | 参考値 |
| **終了基準** | exit criteria | そのレベルを閉じてよい条件 | 完了・DONE |
| **欠陥** | defect | 開始状態・操作・結果・期待が示された不具合。重要度はブロッカー／非ブロッカーの2段（§8） | 問題・気づき |
| **NOT-RUN** | not run | 現在の版に対してそのテストの結果が無い | 未再テスト |
| **未測定（UNMEASURED）** | not measured | まだ一度も測っていない。「問題なし」ではない | — |

`scripts/test.mjs` の出力の語: `Result: PASS` / `FAIL`。

## 3. アプローチ（テストレベルと担当）

| レベル | 種類（ISTQB） | 何を | 誰が | 終了基準 |
| --- | --- | --- | --- | --- |
| **L1** | コンポーネントテスト（自動） | ふつうの関数のロジック・データの検証 | 生成AI（`node scripts/test.mjs`） | 全部 PASS（0 件でない） |
| **L2** | 統合テスト（自動） | HTTP の要求と応答・DB を通す（Workers なら `@cloudflare/vitest-pool-workers`） | 生成AI（同上） | 全部 PASS |
| **L3** | 受け入れテスト | 実際の使い方（ローカルで起動して叩く・つないだ画面） | 人間（ユーザー） | ユーザーが確認した |

各レベルは前のレベルの終了が開始基準。L1・L2 が緑でも「できた」と言わない。ゴールの合格判定は design-cycle の §1・§4（AI の判定は作った本人がしない・ユーザーの判定は機械で置き換えない）。

## 4. 合格基準

- `scripts/test.mjs` の最後の行が `Result: PASS`。**テストが 0 件・結果の XML が無い・vitest が無いは合格でない。**
- 機能ごとの合格基準は、その機能の設計書の §0 に書く（design-cycle）。ここには写さない。

## 6. 開始基準・終了基準

| | 開始基準 | 終了基準 |
| --- | --- | --- |
| L1 | 型の確かめが通る（`package.json` に `typecheck` があれば） | 全部 PASS |

## 7. 中断基準と再開基準

- 同じ欠陥の修正で、確認テストが**連続 3 回**落ちたら中断する。回数を増やして解かない。設計（design-cycle §5 の振り分け）か合格基準の側に穴がある。残った欠陥を §8 の形で報告する。
- 再開はユーザーが判断する。
- 無人の回（issue-run）は、仕組みの側の上限（90 分 × 4 回）がこれに当たる。

## 8. 欠陥管理

**欠陥レポート**の形: 開始状態（データ・設定）／操作（要求）／実際の結果／期待した結果／重要度。

| 重要度 | 根拠 | 扱い |
| --- | --- | --- |
| **ブロッカー** | 動かない・落ちる・データの破損・不正な入力が通る・認可を越える・§4 の赤のどれか。開始状態・操作・結果・期待が示されている | 直す。確認テストをテストの 1 本として足す |
| **非ブロッカー** | 支障が無く、より良くしたいもの・メトリクスの赤・感想 | 直さない。合格基準に変換しない。報告書の「未採用の改善」に1行残す |
| 証拠不足 | 操作と支障が特定されていない | 観測箇所だけ確認テスト。支障が確認できなければ扱わない |
| 着手済み | 作業差分がある | 完了させるか、差分を確認して取り下げる。半端に残さない |

**発見を自動で仕事にしない**——ブロッカーだけ直す（CLAUDE.md 原則2）。

## 10. 変更後の再テスト

| 変更 | 再テスト |
| --- | --- |
| 文書・コメントだけ | テストしない（`git diff` でコメントだけか見る） |
| ふつうの関数のロジック | 関係するテストを `--filter` で → 区切りで全部 |
| HTTP の入口・DB・マイグレーション | 関係する結合の試験 → 区切りで全部 |
| 依存（`package.json`） | `npm install` → 型の確かめ → 全部 |
| テストの入口（`scripts/test.mjs`） | 0 件で FAIL・XML が無ければ FAIL・落ちるテストで FAIL、を小さく確かめる |

## 11. 変えてはいけないこと

- テストを緑に合わせて弱めない・消さない。期待値を実装に合わせて書き換えない（直すのは実装か、設計を直してからテスト）。
- 旧結果を編集しない。
